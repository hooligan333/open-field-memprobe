# memprobe

A probe pack for [open-field issue #15](https://github.com/LaP0573/open-field/issues/15#issuecomment-7141311537). It checks whether anything on the unit writes into the two stretches of DDR that OS 1.7.3 appears never to use:

- **A:** `0x83800000`–`0x84000000` (8 MiB)
- **B:** `0x84d30000`–`0x88000000` (~51 MiB)
- **C:** `0x88040000`–`0x8c000000` (~64 MiB)

Version 3 leaves out `0x88000000`–`0x8803bfff`: version 2 found it written while the screen changed, and it turned out to be the display's second framebuffer (`src/bf/display.cpp` keeps its address in a data word; the first framebuffer is at `0x8c000000`, just past C).

It is a level-1 card pack that needs `base.pack`. It changes no place of the firmware, so it cannot stop the unit from starting. Each frame it works on 16 KiB on the display thread, about 0.3 ms idle. From version 2 it does no work on a frame that comes more than 25 ms after the one before (the display already slowed, as while the tape records); a write made meanwhile is still caught at the block's next look. A pass takes about four minutes on an idle unit, longer while it is busy.

## Modes

| Mode | How | What it does | Risk |
| --- | --- | --- | --- |
| **READ** | copy `memprobe.pack` into `packs/` | Pass 1 checksums every 64 KiB block. Each later pass checksums them again and logs every block whose checksum changed | None: it only reads |
| **WRITE** | copy `memprobe-w.pack` into `packs/` (if `memprobe.pack` is there too, it stands aside and logs that it did) | Pass 1 fills both stretches with a pattern built from each word's address. Each later pass checks every word, logs the first ones that differ and writes the pattern back | If the firmware did use that memory after all, this could disturb it. Run it only after a clean READ session, with tapes and sounds backed up |

## How to run it

1. In disk mode, copy `memprobe.pack` into `packs/` and restart.
2. Use the unit hard for a long session:
   - record on all four tape tracks
   - lift and drop audio
   - sample with the mic and line in
   - play every synth engine and effect
   - run a sequencer
   - use USB audio and disk mode
   - let it sleep and wake again
3. Copy the logs off the unit (`logs/`) and search for lines tagged `memprobe`.
4. If READ was clean, swap in `memprobe-w.pack` and do the same again.
5. To remove it, delete `memprobe.pack` / `memprobe-w.pack` from `packs/`.

## What the log says

```
memprobe 3: mode READ (checksums only, nothing written); watching 0x83800000-0x84000000, 0x84d30000-0x88000000 and 0x88040000-0x8c000000, 1961 blocks of 64 KiB, a quarter a frame
memprobe: first checksums of 1961 blocks taken in 226000 ms (0 slow frames passed over); 0 of 32129024 words were 0
memprobe: pass 1 done in 226000 ms (0 slow frames passed over), 0 block(s) changed in it, 0 in all since the start
```

- **"0 block(s) changed" on every pass:** nothing else touched these stretches during that session. That's the result issue #15 needs.
- **A `block 0x… changed` or `word 0x… holds …` line (a warning):** something does write there. The address says where. At most 32 such lines are logged per start.
- **The count of zero words in the first pass:** how the memory looked at start. Mostly zero would suggest something cleared it; mostly random would suggest nothing has touched it since power-on.

Pass lines appear for the first five passes, then every tenth pass, plus any pass that found a change.

## Build status

Built with open-field's `pack_build.py build3` (main at 378eb86). `pack_build.py check` and `publish_check.py` pass. The per-frame time above is an estimate from the compiled loop (about 11 instructions per word). The base logs the real figure as `cards: 'memprobe' frame call: …`.

## Files

`memprobe.pack` (READ) and `memprobe-w.pack` (WRITE) are built from the same `source/memprobe.cpp`; `memprobe_w.cpp` only switches the mode. `source/` also holds both recipes and their cards (generated by `pack_build.py card`). To rebuild, copy `source/` into an open-field tree as `examples/memprobe/` and run `pack_build.py build3` with `recipe.json` or `recipe_w.json`.

## Results so far (OS 1.7.3, base 32, one unit, 2026-11-24)

- **READ v2, 29 min, 11 passes** (tape recording, lift/drop incl. 8 tracks lift-all/drop-all, mic and radio sampling, USB audio, MTP): only `0x88000000`–`0x8803ffff` changed. That turned out to be the display's second frame buffer, so v3 leaves it out. Nothing else changed.
- **WRITE v3, ~11 min, fill + 3 verify passes:** every word held its pattern.
